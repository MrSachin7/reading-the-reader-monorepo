\section{Anatomy of an Experiment Session}
\label{sec:impl-session}
% Authoring brief for this section lives in section.md (§6.2). The spine of the chapter.
% Rewritten as a top-down, frontend-first flow: the researcher acts on a screen, the

\Cref{sec:impl-structure} mapped where the code lives; this section sets it in motion by following one experiment session end to end, told from the two screens the researcher operates and tracing each action inward to the code that answers it.
It is the concrete counterpart of the abstract adaptive loop of \cref{sec:design-loop}, and it is the part of the system a researcher actually drives.

\subsection*{Two screens, two channels}

The platform is operated as two browser surfaces backed by one Next.js front-end (\cref{sec:impl-structure}), shown together in \cref{fig:impl-screens}: a researcher console on the operator's screen and a participant reader on the second screen.
The researcher prepares and steers the session from the console, monitoring a live mirror of what the participant sees, while the participant only ever sees the reader; the two are kept consistent not by talking to each other but by both rendering the same backend-owned snapshot.

Two channels connect the front-end to the backend, and the distinction between them organises the whole walkthrough: a request and response REST interface carries the researcher's discrete \emph{commands}, while a single long-lived WebSocket carries the continuous realtime \emph{stream} in both directions.
\Cref{fig:impl-flow} traces a complete session across these two channels, from the researcher's first command to the sealed record; the rest of this subsection then shows the code that realises each channel.

Commands travel over REST.
The front-end's REST access is centralised in RTK Query slices (\cref{sec:impl-structure}); each researcher command (save the participant, choose the material, start the session, finish it, change an intervention policy) is a mutation that posts to a FastEndpoints route and receives the updated \texttt{ExperimentSessionSnapshot} in reply.
\Cref{lst:impl-rest-command} shows two of them: starting and finishing the session.
Marking each mutation as invalidating the \texttt{Experiment} cache tag means that after any command the front-end re-reads the authoritative state rather than trusting a locally computed one.

\begin{listing}[htbp]
\begin{minted}{typescript}
export const experimentSessionApi = baseApi.injectEndpoints({
  endpoints: (builder) => ({
    startExperimentSession: builder.mutation<void, void>({
      query: () => ({ url: "/eyetrackers/start", method: "POST" }),
      invalidatesTags: ["Experiment"],
    }),
    finishExperimentSession: builder.mutation<ExperimentSessionSnapshot, { source: string }>({
      query: (body) => ({ url: "/experiment-session/finish", method: "POST", body }),
      invalidatesTags: ["Experiment"],
    }),
    // ...participant, reading-material, decision- and intervention-policy commands...
  }),
})
\end{minted}
\caption{Researcher commands as RTK Query mutations (abbreviated from \texttt{redux/api/experiment-session-api.ts}).}
\label{lst:impl-rest-command}
\end{listing}

The realtime stream travels over the WebSocket.
On the client a single connection is shared across the whole front-end by the \texttt{gaze-socket} module (\cref{lst:impl-ws-client}): it connects lazily, and on open it asks for the current state and re-establishes any subscriptions, then routes every inbound frame through one handler.
On the server the \texttt{/ws} endpoint is deliberately just as thin (\cref{lst:impl-ws-server}): it accepts the socket, reads each text frame as a typed envelope, and forwards it as a command to the session manager through an ingress interface, so the transport layer holds no session logic of its own.

\begin{listing}[htbp]
\begin{minted}{typescript}
function connect() {
  if (socket?.readyState === WebSocket.OPEN ||
      socket?.readyState === WebSocket.CONNECTING) return;
  socket = new WebSocket(getWsUrl());            // ws(s)://host/ws
  socket.addEventListener("open", () => {
    requestExperimentState();                    // pull the current snapshot
    if (wantsGazeSubscription) send({ type: "subscribeGazeData", payload: {} });
    startPingLoop();
  });
  socket.addEventListener("message", handleMessage);   // route every ServerEnvelope
  socket.addEventListener("close", scheduleReconnect); // reconnect after 1s
}
\end{minted}
\caption{Shared WebSocket client (abbreviated from \texttt{lib/gaze-socket.ts}).}
\label{lst:impl-ws-client}
\end{listing}

\begin{listing}[htbp]
\begin{minted}{csharp}
app.Map("/ws", async (HttpContext context, WebSocketConnectionManager connections,
                      IExperimentCommandIngress ingress) =>
{
    using var socket = await context.WebSockets.AcceptWebSocketAsync();
    var connectionId = connections.Add(socket);
    while (socket.State == WebSocketState.Open && !context.RequestAborted.IsCancellationRequested)

    }
});
\end{minted}

\label{lst:impl-ws-server}
\end{listing}

Each frame the server sends back is a small JSON envelope tagged with a message type and a server timestamp.
Because no client code is generated from the backend (\cref{sec:impl-structure}), the front-end mirrors the backend's message catalogue by hand as the discriminated union in \cref{lst:impl-envelope}, in which the three lifecycle messages all carry the same \texttt{ExperimentSessionSnapshot} the manager assembled.
Both screens therefore render directly from the authoritative snapshot rather than recomputing session state, which is what keeps them consistent without drift; the cost is that this union and the backend's message-type constants must be aligned by discipline, a seam revisited in \cref{sec:impl-engineering}.

\begin{listing}[htbp]
\begin{minted}{typescript}
type ServerEnvelope =
  | { type: "gazeSample"; sentAtUnixMs: number; payload: GazeData }
  | { type: "experimentStarted" | "experimentStopped" | "experimentState";
      sentAtUnixMs: number; payload: ExperimentSessionSnapshot }
  | { type: "readingFocusChanged"; sentAtUnixMs: number; payload: ReadingFocusSnapshot }
  | { type: "interventionEvent"; sentAtUnixMs: number; payload: InterventionEventSnapshot }
  // ...one further variant per backend message type...
  | { type: "error"; sentAtUnixMs: number; payload: { message: string } };
\end{minted}
\caption{Front-end inbound message union (abbreviated from \texttt{lib/gaze-socket.ts}). Hand-mirrored from the backend message catalogue; lifecycle variants carry \texttt{ExperimentSessionSnapshot}.}

\end{listing}

\subsection*{Configuring: preparing the session}

In the configuring phase the researcher prepares the session through a guided, role-sequenced stepper, shown in \cref{fig:impl-setup}.
Each step is a REST command of the kind in \cref{lst:impl-rest-command}: selecting the participant, for example, posts to the participant route.
On the backend every route is a thin FastEndpoints handler that maps the request onto the \texttt{IExperimentRuntimeAuthority} port and returns the updated snapshot, holding no logic of its own; the pattern is identical across routes, so it is shown once, for the finish command, in \cref{lst:impl-endpoint}.
The participant handler calls \texttt{SetCurrentParticipantAsync} on the session manager, which shows the shape every state-changing command takes (\cref{lst:impl-state-change}): it awaits the lifecycle gate, publishes a new immutable session record with \texttt{Volatile.Write}, and persists a checkpoint before releasing the gate, copying the participant so that no caller can mutate published state.
The gate is a one-permit \texttt{SemaphoreSlim} rather than a plain lock because these operations are asynchronous and may \texttt{await}, and it serialises the slow command path so that, for example, one request cannot start a session while another is still stopping it.

\begin{listing}[htbp]
\begin{minted}{csharp}
public async ValueTask SetCurrentParticipantAsync(
    Participant participant, CancellationToken ct = default)
{
    await _lifecycleGate.WaitAsync(ct);                 // serialise the command path
    try
    {
        var current = Volatile.Read(ref _session);
        Volatile.Write(ref _session,
            current with { Participant = participant.Copy() });   // publish new state
        await SaveCurrentCheckpointAsync(ct);                     // persist a checkpoint
    }
    finally
    {
        _lifecycleGate.Release();
    }
}
\end{minted}
\caption{Template for every state-changing command (from \texttt{ExperimentSessionManager.Lifecycle.cs}).}
\label{lst:impl-state-change}
\end{listing}

The backend tracks four independent readiness gates, a participant, a selected eye tracker with a valid licence, a passed calibration, and the reading material, each of which reports whether it is satisfied and, if not, the reason it blocks the start.
The stepper sequences these into a recommended order, researcher preparation (the eye tracker and the reading material) before participant setup (the participant details and calibration), and locks each step until its prerequisites are met, so the researcher is never offered a control that cannot yet be used.
The eye-tracker step in the figure shows the detail of this preparation: a real Tobii device is selected and its licence is managed, with an explicit overwrite guard so that a saved licence is not replaced by accident.

Calibration is one of the four gates and runs as its own immersive sub-flow, shown in \cref{fig:impl-calibration}.
The participant follows a sequence of on-screen targets (a configurable number of points) while the device collects samples, after which a calibration is computed and applied and a validation pass measures its accuracy and precision.
Only a calibration whose validation passes satisfies the gate, and the accuracy and precision it reports are carried in the setup snapshot and evaluated in \cref{ch:evaluation}.

\subsection*{Starting: committing to the run}

When all four gates are satisfied the researcher starts the session from the console, which sends the \texttt{startExperimentSession} mutation of \cref{lst:impl-rest-command}; on the backend this resolves to \texttt{StartSessionAsync} (\cref{lst:impl-start}), which re-checks readiness before committing to the run.
If anything is incomplete it refuses with the blocking step's reason, so a misconfigured run cannot be started rather than merely being discouraged; otherwise it resolves the order of the experiment's material items (fixed or randomised), resets the gaze counters and the event sequence, and marks the session active.
The readiness re-check matters because the gates are also the front-end's, and a control surface can lag the truth by a frame; performing the same check on the authoritative state at the moment of commit means the gating is enforced by the backend rather than merely reflected in a disabled button.
Only after the check passes does the manager publish the now-active session and broadcast the \texttt{experimentStarted} snapshot, which flips both screens into the running phase at once.

\begin{listing}[htbp]
\begin{minted}{csharp}
public async Task<bool> StartSessionAsync(CancellationToken ct = default)
{
    await _lifecycleGate.WaitAsync(ct);
    try
    {
        var current = Volatile.Read(ref _session);
        if (current.IsActive) return false;

        EnsureSetupIsReadyForStart(current, _calibrationSnapshot, _liveReadingSession);
        ResolveExperimentOrderForStart();                  // fixed or randomised order

        Interlocked.Exchange(ref _receivedGazeSamples, 0);
        Volatile.Write(ref _session,
            ExperimentSession.StartNew(startedAt, current.Participant, current.EyeTrackerDevice));
        // ...initialise the replay-recovery buffer for this session...
        var snapshot = GetCurrentSnapshot();
        await _clientBroadcasterAdapter.BroadcastAsync(
            MessageTypes.ExperimentStarted, snapshot, ct);
        return true;
    }
    finally { _lifecycleGate.Release(); }
}
\end{minted}
\caption{Session start (abbreviated from \texttt{ExperimentSessionManager.Lifecycle.cs}). Re-checks all readiness gates at the moment of commit before publishing and broadcasting the snapshot.}
\label{lst:impl-start}
\end{listing}

The broadcast is the work of the client broadcaster (\cref{lst:impl-broadcaster}), the infrastructure adapter that realises \texttt{IClientBroadcasterAdapter}: it serialises the snapshot into one envelope (the \texttt{ServerEnvelope} shape of \cref{lst:impl-envelope}) and sends it to every open socket, silently skipping any that have dropped, so a single call reaches both screens at once.

\begin{listing}[htbp]
\begin{minted}{csharp}
public sealed class WebSocketRealtimeMessenger : IClientBroadcasterAdapter
{
    private readonly WebSocketConnectionManager _connections;
    public int ConnectedClients => _connections.Count;

    public async ValueTask BroadcastAsync<T>(
        string messageType, T payload, CancellationToken ct = default)
    {
        var buffer = SerializeEnvelope(messageType, payload);  // { type, sentAtUnixMs, payload }
        foreach (var socket in _connections.All)
        {
            if (socket.State != WebSocketState.Open) continue;
            try { await socket.SendAsync(buffer, WebSocketMessageType.Text, true, ct); }
            catch (OperationCanceledException) { throw; }
            catch { /* ignore disconnected sockets and send failures */ }
        }
    }
}
\end{minted}
\caption{Client broadcaster (abbreviated from \texttt{ReadingTheReader.RealtimeMessenger}). Realises \texttt{IClientBroadcasterAdapter}: one serialised envelope fanned out to every open socket.}
\label{lst:impl-broadcaster}
\end{listing}

\subsection*{Running: reading with the live adaptive loop}

From this point the realtime channel does the work.
The gaze that drives it originates in the sensing adapter (\cref{lst:impl-tobii}): \texttt{TobiiEyeTrackerAdapter} realises \texttt{IEyeTrackerAdapter}, subscribes to the Tobii SDK's gaze callback, maps each raw sample into the domain's \texttt{GazeData}, and raises \texttt{GazeDataReceived} for the manager to consume.
The whole adapter is compiled behind a \texttt{\#if WINDOWS} guard because the Tobii SDK is Windows-only, with a mock tracker compiled in its place off-Windows so the rest of the system builds and runs on any platform.

\begin{listing}[htbp]
\begin{minted}{csharp}
#if WINDOWS
public class TobiiEyeTrackerAdapter : IEyeTrackerAdapter
{
    public event EventHandler<GazeData>? GazeDataReceived;
    private IEyeTracker? _selectedTracker;

    public Task StartEyeTracking()
    {
        // ...guards: a tracker is selected, not calibrating or validating...
        _selectedTracker!.GazeDataReceived += OnTobiiGazeDataReceived;   // Tobii SDK event
        return Task.CompletedTask;
    }

    private void OnTobiiGazeDataReceived(object? sender, GazeDataEventArgs e)
    {
        var gazeData = new GazeData {
            DeviceTimeStamp = e.DeviceTimeStamp,
            LeftEyeX = (float)e.LeftEye.GazePoint.PositionOnDisplayArea.X,
            LeftEyeY = (float)e.LeftEye.GazePoint.PositionOnDisplayArea.Y,
            // ...right eye, pupil, and gaze-origin fields...
        };
        gazeData.Sanitize();
        GazeDataReceived?.Invoke(this, gazeData);   // -> ExperimentSessionManager
    }
}
#endif   // a mock tracker is compiled in this class's place off-Windows
\end{minted}
\caption{Tobii sensing adapter (abbreviated from \texttt{TobiiEyeTracker\-Adapter.cs}). Realises \texttt{IEyeTrackerAdapter}; the \texttt{\#if WINDOWS} guard keeps the SDK out of non-Windows builds, where a mock fills its place.}
\label{lst:impl-tobii}
\end{listing}

The manager consumes those samples on a lock-free path (examined in \cref{sec:impl-highlights}) and broadcasts the resulting snapshot, and both screens consume it through one small hook, \texttt{useLiveExperimentSession} (\cref{lst:impl-live-hook}).
Because the manager re-emits the snapshot several times per gaze observation (focus, attention summary, and analysis each update it), the hook coalesces those bursts to a single React commit per animation frame, so the live tree re-renders at roughly \SI{60}{\hertz} regardless of the inbound message rate while never dropping the newest snapshot.
The adaptive loop of \cref{sec:design-loop} runs over the modules resolved from the registries of \cref{sec:design-modules} as these samples arrive.

\begin{listing}[htbp]
\begin{minted}{typescript}
export function useLiveExperimentSession() {
  const [session, setSession] = useState<ExperimentSessionSnapshot | null>(null);
  useEffect(() => {
    // Coalesce snapshot bursts to one React commit per animation frame (~60Hz).
    let latest = null, hasPending = false, frameId = null;
    const flush = () => {
      frameId = null;
      if (hasPending) { hasPending = false; setSession(latest); }
    };
    const unsubscribe = subscribeToExperimentSession((next) => {
      latest = next; hasPending = true;
      if (frameId === null) frameId = requestAnimationFrame(flush);
    });
    requestExperimentState();
    return () => { unsubscribe(); if (frameId !== null) cancelAnimationFrame(frameId); };
  }, []);
  return session;
}
\end{minted}
\caption{Live-session hook shared by both screens (abbreviated from \texttt{lib/use-live-experiment-session.ts}). Coalesces snapshot bursts to one React commit per animation frame (\(\approx\)\SI{60}{\hertz}).}
\label{lst:impl-live-hook}
\end{listing}

The participant sees only the reader (\cref{fig:impl-screens-reader}), where the text adapts in place under the loop.
In code the reader is the producing counterpart of the console (\cref{lst:impl-reader}): on an active session it registers its view, streams each enriched gaze and focus sample back over the WebSocket as the participant reads, and renders the text from the presentation carried on the snapshot.

\begin{listing}[htbp]
\begin{minted}{typescript}
const liveSession = useLiveExperimentSession();        // the same hook the console uses
useEffect(() => {
  if (!liveSession?.isActive) return;
  registerParticipantView();                           // join the realtime session
  return () => unregisterParticipantView();
}, [liveSession?.isActive]);

// Stream each enriched gaze + focus sample back over the WebSocket while reading:
const handleEnrichedFocusSample = (sample: GazeData, focus: GazeFocusState) =>
  updateReadingEnrichedGazeSample(sample, { ...focus }, focus.updatedAtUnixMs);

return <ReaderShell markdown={markdown} presentation={presentation}
                    onEnrichedFocusSample={handleEnrichedFocusSample} />;
\end{minted}
\caption{Participant reader (abbreviated from \texttt{ReadingPage.tsx}): registers the view, renders text from the snapshot presentation, and streams enriched gaze samples over the WebSocket.}
\label{lst:impl-reader}
\end{listing}

The researcher observes and steers the same session through the live control surface (\cref{fig:impl-screens-console}), the second screen of \cref{sec:design-style}: it mirrors the participant's text with the live eye-movement analysis drawn over it (the fixations, saccades, and regressions toggled by the legend at the top), reports the live end-to-end latency, and offers the manual interventions and typography controls through which the researcher adapts the presentation.
The overlay is computed from the same gaze stream and carried on the same snapshot the screens already render, so the researcher sees where the participant is reading, and where they are regressing, without any additional channel.
Its behaviour makes the commit discipline of driver~D7 visible in the interface, since appearance changes are applied immediately whereas typography changes wait for the selected boundary, which is the two-phase, context-preserving commit of \cref{sec:design-loop} exposed as an operator control.
In code the console is the consuming counterpart of the reader (\cref{lst:impl-console}): it reads the same snapshot through the same hook, renders the mirror and the overlays from it, issues policy changes as REST mutations, and pushes a manual intervention straight over the WebSocket.

\begin{listing}[htbp]
\begin{minted}{typescript}
const session = useLiveExperimentSession();            // live snapshot, mirrored on screen
const [updateInterventionPolicy] = useUpdateInterventionPolicyMutation();  // REST command

// A manual intervention the researcher applies is pushed over the WebSocket:
const applyManualIntervention = (next: InterventionChoice, reason: string) =>
  applyInterventionCommand({
    source: "manual", trigger: "researcher-ui", reason,
    moduleId: next.moduleId, parameters: next.parameters,
  });
\end{minted}
\caption{Researcher console (abbreviated from \texttt{researcher/current-live/index.tsx}): drives the gaze mirror and overlays from the live snapshot, issues policy changes as REST mutations, and pushes manual interventions over the WebSocket.}
\label{lst:impl-console}
\end{listing}

The session then proceeds item by item.
For each material the participant reads while the loop adapts the text, and afterwards answers a short comprehension quiz submitted over REST, and both the reading events and the answers are written into the session record alongside every gaze sample, intervention, and lifecycle event.

\subsection*{Finishing: sealing and replaying the record}

Finishing the session ends it and seals its record.
The researcher's \texttt{finishExperimentSession} command (\cref{lst:impl-rest-command}) lands on its FastEndpoints handler (\cref{lst:impl-endpoint}), which forwards it to the runtime authority and returns the sealed snapshot, the thin-handler shape every REST route in the system follows.

\begin{listing}[htbp]
\begin{minted}{csharp}
public sealed class FinishExperimentEndpoint
    : Endpoint<FinishExperimentRequest, ExperimentSessionSnapshot>
{
    private readonly IExperimentRuntimeAuthority _runtimeAuthority;
    public FinishExperimentEndpoint(IExperimentRuntimeAuthority runtimeAuthority)
        => _runtimeAuthority = runtimeAuthority;

    public override void Configure() => Post("/experiment-session/finish");

    public override async Task HandleAsync(FinishExperimentRequest req, CancellationToken ct)
    {
        var snapshot = await _runtimeAuthority.FinishSessionAsync(
            new FinishExperimentCommand(req.Source), ct);
        await Send.OkAsync(snapshot, ct);
    }
}
\end{minted}
\caption{A REST endpoint (abbreviated from \texttt{FinishExperimentEndpoint.cs}). Depends on a core port, maps the request to an application command, and returns the snapshot; no logic in the transport layer.}
\label{lst:impl-endpoint}
\end{listing}

On the manager this resolves to \texttt{FinishSessionAsync}: it stops the loop, flushes any buffered events, and builds two exports from the recovery buffer, a full raw export and a processed one, saves them as the latest, marks the recovery completed, and clears the active record, after which the session is sealed exactly as \cref{sec:design-data} described.
A sealed session is then available for replay, shown in \cref{fig:impl-replay}: the recording is reconstructed as a timed playback, with the gaze token heat map drawn over the text and a filterable timeline of lifecycle, quiz, and intervention events beside it.
Replay is therefore the operational proof of \cref{sec:design-data}, that a session can be re-presented and re-analysed from its record alone.

\subsection*{Where it all converges}

Every command and every realtime frame in this walkthrough meets at one component, the \texttt{ExperimentSessionManager}, which is the one place the session's state lives.
Its responsibilities are divided by concern across partial classes (a lifecycle facet, a gaze facet, and analysis, decision, intervention, and replay facets), but they share one object and reach the rest of the system only through ports.
In source this is a single \mbox{C\#} class declared \texttt{sealed partial} and spread across a dozen files, one per concern, which together realise the four runtime interfaces the rest of the system depends on and hold their shared state in a handful of private fields, as \cref{lst:impl-manager-class} abbreviates.
The split is purely a source-level organisation: the concerns compile into one type and one object, so the gaze facet and the lifecycle facet act on the same \texttt{\_session} field behind the same \texttt{\_lifecycleGate}, and no concern can hold a private copy of the session that the others cannot see.

\begin{listing}[htbp]
\begin{minted}{csharp}

Crucially, the manager names none of the concrete adapters it drives: it depends only on the port interfaces declared beside it in \texttt{Application}, so the Tobii device, the client broadcaster, and the persistence store are each reached through a port alone.
That seam, where any adapter (or a future external module) plugs in behind a core-declared interface, is where the modularity of \cref{sec:design-style} is realised at the level of individual classes, and it is examined in \cref{sec:impl-highlights}.
Because all session state lives behind this one component and is published as a single snapshot, the researcher's control surface and the participant's reader never hold competing copies of the truth.

The walkthrough has named several mechanisms only in passing: the lock-free gaze path that keeps the live latency low, the ports-and-adapters seam that makes the sensing, broadcast, and persistence modules swappable, and the export that replay consumes.
\Cref{sec:impl-highlights} opens these for a closer look.
