\subsection{Pluggable modules and the external-provider contract}
\label{sec:impl-modularity}

The architecture's central promise (RQ1) is that sensing, eye-movement analysis, decision strategy, and intervention execution are modules behind stable contracts, so a new intervention or a new decision or analysis provider can be added without modifying the core reading runtime.
This is realised through two complementary mechanisms that meet the core through the same ports: an \emph{in-process} module registry for modules that ship with the platform, and an \emph{out-of-process} module-provider framework for external, possibly AI-driven, services.
\Cref{fig:impl-session-manager} shows the seam they share: the \texttt{ExperimentSessionManager} depends only on the port interfaces declared in \texttt{Application}, and every concrete realisation (a hardware adapter, the broadcaster, the persistence store, or a module) plugs in from the infrastructure side, so a dependency never points outward from the core.

\paragraph{In-process modules.}
A module that ships with the platform satisfies one small interface, \cref{lst:impl-module-contract}: it exposes a descriptor declaring its identifier and parameters, validates a request, and executes it against the current presentation.
The runtime never names a concrete module; it asks the registry to resolve one by identifier, so the set of modules is open.
The eight built-in intervention modules required by FR7.5 (font family, font size, line width, line height, letter spacing, theme mode, palette, and the participant-edit lock) are simply entries in the registry's list, and adding a ninth is a matter of implementing the interface and registering it, with no change to the runtime or to any existing module (FR7.1--FR7.3).
The same shape recurs for the other concerns: decision strategies and eye-movement analysis strategies are resolved from their own registries, so a built-in rule-based decider or fixation detector can be swapped without touching the loop that drives them.

\begin{listing}[htbp]
\begin{minted}{csharp}
public interface IReadingInterventionModule
{
    ReadingInterventionModuleDescriptor Descriptor { get; }      // id + declared parameters
    ReadingInterventionValidationResult Validate(ReadingInterventionRequest request);
    ReadingInterventionModuleExecutionResult Execute(
        ReadingInterventionExecutionContext context, ReadingInterventionRequest request);
}

public interface IReadingInterventionModuleRegistry
{
    IReadOnlyList<ReadingInterventionModuleDescriptor> List();
    bool TryResolve(string? moduleId, out IReadingInterventionModule? module);
}
\end{minted}
\caption{The in-process module contract (from \texttt{Interventions/}). A module declares its parameters, validates a request, and executes it; the runtime only ever resolves a module from the registry by identifier, so adding one means implementing this interface and registering it, with no change to the runtime or any existing module.}
\label{lst:impl-module-contract}
\end{listing}

\paragraph{External providers.}
The same concern can instead be fulfilled by an external process, which is how the platform admits AI-driven deciders or third-party analysers without building them into this repository (the architectural, not end-to-end, scope of \cref{sec:final-problem-statement}).
An external service connects over a dedicated WebSocket and speaks the documented module-provider protocol of \cref{lst:impl-provider-protocol} (FR19.4): it sends a \texttt{Hello} declaring its identifier and the modules and capabilities it can serve, and the system replies with a \texttt{Welcome} listing the modules it has accepted, or an error if the protocol or a module identifier does not match.
Once registered, per-module context flows to the provider as \texttt{Inbound} envelopes and its decisions return as \texttt{Outbound} envelopes, which are applied through exactly the same validation and logging path as a built-in module, so an external decision is indistinguishable downstream from an internal one (FR19.2).
A provider that stops sending heartbeats, or disconnects outright, is dropped by the gateway and the affected strategy degrades to its built-in fallback rather than stalling the experiment, with the transition recorded in the session log (FR19.3); \cref{fig:impl-provider-seq} traces this lifecycle.

\subsection{The sensing pipeline: from gaze to oculomotor events}
\label{sec:impl-sensing}

RQ2 asks how a raw Tobii stream becomes oculomotor events, fixations, saccades, and regressions, fast enough for live adaptation and in a way that is inspectable and reproducible.
The platform answers this with a three-stage pipeline (\cref{fig:impl-pipeline}) that is split across the tiers along a deliberate line: \emph{acquisition} and \emph{temporal analysis} run on the backend where the session state lives, while the \emph{spatial} mapping from a gaze point to a word runs on the front-end where the rendered layout lives.
The two halves meet at one stable contract, a token-indexed reading observation, so neither side needs the other's concerns.

\paragraph{Acquisition on a lock-free path.}
Each sample the sensing adapter raises (\cref{lst:impl-tobii}) is taken by the session manager on a path that never touches the lifecycle gate that serialises the control commands of \cref{sec:impl-session}.
The manager keeps a clear split between this \emph{data plane} and the \emph{control plane}: the gate orders the slow, awaitable lifecycle operations, whereas the gaze path uses only an atomic counter and a volatile publish (\cref{lst:impl-hotpath}), so a sample is recorded and fanned out without waiting on any lock.
This is what keeps the end-to-end latency within the budget that live adaptation needs; the measured figure is reported in \cref{ch:evaluation}.

\begin{listing}[htbp]
\begin{minted}{csharp}
public void UpdateGazeSample(GazeData gazeData)
{
    gazeData.Sanitize();
    Interlocked.Increment(ref _receivedGazeSamples);    // atomic counter, no lock
    Volatile.Write(ref _latestGazeSample, gazeData);     // publish without the lifecycle gate
    RecordGazeSample(DateTimeOffset.UtcNow.ToUnixTimeMilliseconds(), gazeData);
}
\end{minted}
\caption{The lock-free ingest on the gaze data plane (from \texttt{ExperimentSessionManager.Gaze.cs}). It uses an \texttt{Interlocked} counter and a \texttt{Volatile} publish rather than the lifecycle gate, so high-frequency gaze samples are never blocked behind the slower control-plane operations.}
\label{lst:impl-hotpath}
\end{listing}

\paragraph{Spatial mapping in the reader.}
Mapping a gaze point to a word is done in the participant reader because only the reader knows where each word was actually laid out.
The reader normalises each sample to a screen point (FR4.2), then maps it to the nearest word token (\cref{lst:impl-tokenmap}, FR4.3): it scores the rendered word boxes, choosing the best line first (biased towards the line already being read, which absorbs vertical jitter) and then the nearest word on that line.
Choosing the line is the part that most affects stability, so it is scored explicitly (\cref{fig:impl-gazemap}): each line is reduced to a vertical band (its top, bottom, and centre), and a sample is charged for how far it falls outside the band, weighted heavily, plus a smaller pull towards the band centre that breaks ties, with the lowest-scoring band winning.
A fixed discount is then subtracted from the score of the line already being read, which acts as hysteresis: a sample that strays slightly above or below the current line stays attributed to it rather than flickering to a neighbour, the failure mode that vertical gaze jitter of the order of the line spacing would otherwise produce.
Only once the line is fixed is the word chosen, by horizontal distance to each word box on that line, so vertical noise can no longer pull the mapping to a word that merely happens to sit nearby in an adjacent line.
Re-measuring the word boxes from the live document is the property that lets the area-of-interest mapping survive reflow, and it is a first-class strength of the AOI choice rather than an implementation detail (FR5.4).
The boxes are refreshed from the rendered DOM whenever it changes, prompted by mutation, resize, and scroll observers, so a typographic intervention that reflows the whole page (a larger font or a narrower measure) moves every word to a new position without invalidating the mapping, because the next gaze sample is hit-tested against the boxes as they are now rather than against coordinates baked in at load.
This is exactly the failure mode a coordinate-based detector would suffer, and avoiding it is why the analysis reasons over word tokens rather than raw screen positions.
The same live measurement also makes the mapping independent of screen resolution and window size, since the normalised gaze sample is scaled to the current viewport and matched against boxes measured in that same space.
The result is published as a token-indexed observation carrying the token identifier, its token, line, and block indices, and whether the gaze is inside the reading area; this observation is the stable interface (FR4.4) the analysis layer and the export both consume.

\begin{listing}[htbp]
\begin{minted}{typescript}
// getAxisDistance(p, lo, hi): 0 if p is inside [lo, hi], else the gap to the nearer edge.

// Stage 1 -- choose the line. Each line is collapsed to a vertical band; the band
// closest to y wins, with a standing discount for the line already being read.
function pickBestLine(layouts: WordLayout[], y: number, activeIndex: number | null) {
  const preferredLine = activeIndex === null ? null : layouts[activeIndex]?.line ?? null;
  // collapse word boxes into one vertical band per line { line, top, bottom, centerY }
  const bands = new Map<number, LineRange>();
  for (const w of layouts) {
    const b = bands.get(w.line);
    if (!b) { bands.set(w.line, { line: w.line, top: w.top, bottom: w.bottom, centerY: w.centerY }); continue; }
    b.top = Math.min(b.top, w.top); b.bottom = Math.max(b.bottom, w.bottom);
    b.centerY = (b.centerY + w.centerY) / 2;
  }
  let bestLine: number | null = null, bestScore = Infinity;
  for (const b of bands.values()) {
    let score = getAxisDistance(y, b.top, b.bottom) * 14     // distance outside the band (weighted hard)
              + Math.abs(b.centerY - y) * 0.45;              // gentler pull to the band centre (tie-break)
    if (b.line === preferredLine) score -= 24;               // hysteresis: hold the current line
    if (score < bestScore) { bestScore = score; bestLine = b.line; }
  }
  return bestLine;
}

// Stage 2 -- choose the word on that line by horizontal distance to its box. Word boxes are
// re-measured from the live DOM, so the mapping survives presentation changes (FR5.4).
function pickWordIndex(layouts: WordLayout[], x: number, y: number, activeIndex: number | null) {
  const bestLine = pickBestLine(layouts, y, activeIndex);
  let bestIndex: number | null = null, bestScore = Infinity;
  for (const w of layouts) {
    if (w.line !== bestLine) continue;
    const score = getAxisDistance(x, w.left, w.right) * 1.35  // horizontal distance to the word box
                + Math.abs(w.centerX - x) * 0.12;
    if (score < bestScore) { bestScore = score; bestIndex = w.index; }
  }
  return bestIndex;                       // -> token id + token/line/block index in the observation
}
\end{minted}
\caption{Gaze-to-content mapping in the reader (abbreviated from \texttt{useGazeTokenHighlight.ts}). The nearest word is chosen by a two-stage score: \texttt{pickBestLine} fixes the line, weighting vertical distance to the line band heavily and discounting the line already being read so jitter does not jump lines, and \texttt{pickWordIndex} then takes the nearest word on that line. \texttt{layouts} is rebuilt from the rendered DOM on every mutation, resize, and scroll, which is what keeps the mapping valid across presentation changes.}
\label{lst:impl-tokenmap}
\end{listing}

\paragraph{Temporal analysis as a replaceable strategy.}
The oculomotor events themselves are derived on the backend by an eye-movement analysis strategy that consumes the stream of observations.
This strategy realises the area-of-interest (I-AOI), dwell-based branch of the fixation-identification taxonomy of Salvucci and Goldberg introduced in \cref{subsec:oculomotor-events}: because the spatial stage has already resolved each gaze point to the word it falls on (\cref{lst:impl-tokenmap}), the word token is itself the area of interest, and a fixation is identified purely from the dwell time accumulated on it, with neither the velocity threshold of I-VT nor the dispersion threshold of I-DT.
This fits reading directly, because it yields events that are already bound to words, the unit over which the downstream decision strategies reason.
The built-in strategy is therefore a dwell detector: a new token is held as a \emph{candidate} and only confirmed as a fixation once it has been dwelt on past a threshold (90\,ms initially, then 70\,ms within a line and 135\,ms across a line change), at which point the previous fixation is finalised and the connecting saccade is built.
The threshold is raised across a line change because that movement is larger and noisier than a within-line step, so a longer dwell is required before the new word is accepted, the same jitter concern that the line hysteresis of \cref{fig:impl-gazemap} addresses spatially.
A finalised fixation is then binned for the rolling per-word attention summary by its total dwell: a dwell under 45\,ms is dropped as noise, one of at least 130\,ms is counted as a fixation, and the band between is recorded as a skim, so the per-word statistics separate words that were read from words the gaze merely crossed.
A saccade's direction is read from the change in line and token index, and a backward step is exactly a regression (\cref{lst:impl-saccade}), which is how the regression count the researcher sees is produced.
Two properties matter for RQ2's ``inspectable and reproducible'' clause.
First, the strategy is a pure function of the observation and the prior state: \texttt{AnalyzeAsync} returns a new immutable runtime state rather than mutating anything, so replaying the same observations yields the same events.
Second, it is resolved from a registry behind the \texttt{IEyeMovementAnalysisStrategy} interface, so the built-in detector can be replaced by an external analysis provider over the contract of \cref{sec:impl-modularity} without changing anything that consumes its output (FR18.2).
The events it produces drive the live overlay on the researcher console (\cref{fig:impl-screens-console}), feed the decision strategies, and are written into the session record (FR18.3).

\begin{listing}[htbp]
\begin{minted}{csharp}
private static SaccadeSnapshot? BuildSaccade(FixationSnapshot? from, FixationSnapshot to)
{
    if (from is null) return null;
    var lineDelta = to.LineIndex - from.LineIndex;
    var direction = lineDelta == 0
        ? to.TokenIndex > from.TokenIndex ? SaccadeDirections.Forward
        : to.TokenIndex < from.TokenIndex ? SaccadeDirections.Backward          // a regression
                                          : SaccadeDirections.Unknown
        : lineDelta > 0 ? SaccadeDirections.LineChangeForward
                        : SaccadeDirections.LineChangeBackward;                   // line regression
    return new SaccadeSnapshot(from.TokenId, to.TokenId, /* indices, timing, */ lineDelta, direction);
}
\end{minted}

\label{lst:impl-saccade}
\end{listing}

\subsection{Tobii SDK integration}
\label{subsec:impl-tobii-sdk}

The sensing pipeline above starts where the gaze stream enters the backend; this subsection opens the hardware boundary at which it starts, namely how the adapter of \cref{lst:impl-tobii} talks to the device through the vendor SDK.
That adapter is the only place in the system that names the Tobii API, and the whole file compiles behind a \texttt{\#if WINDOWS} guard because the \texttt{Tobii.Research.x64} binding is distributed for Windows only (C1); off Windows a mock adapter is compiled in its place, which is what lets the rest of the platform build and run on any machine (\cref{sec:impl-sensing-modes}).

Selecting a device is a discovery step rather than fixed configuration: the adapter calls the SDK's \texttt{FindAllEyeTrackers} and takes the first connected tracker, so no serial number or address is hard-coded and a session runs on whatever Tobii unit is attached.
Before any gaze is allowed to flow, an optional licence is applied: when a licence file is present the adapter wraps its bytes in a \texttt{LicenseKey}, applies it to the selected tracker, and checks that every entry validates as \texttt{Ok}, refusing to proceed on an invalid licence rather than silently running unlicensed.
Once a tracker is selected and licensed, \texttt{StartEyeTracking} subscribes to the SDK's gaze callback, and from that point each callback is translated into the domain's \texttt{GazeData} and raised for the session manager, as \cref{lst:impl-tobii} showed.

Each callback carries a binocular sample, of which the adapter maps the parts the rest of the system needs: the device timestamp, and for each eye the on-display gaze point with its validity, together with the eye position and gaze origin in user coordinates and the pupil measurement.
The detail that matters downstream is that the gaze point arrives as a position on the display area normalised to the unit square rather than in pixels, which is the hardware-side counterpart of the resolution independence established in \cref{sec:impl-sensing}: the device reports where the participant looked as a fraction of the display, the reader maps that fraction onto the live word boxes, and so neither half of the mapping is tied to a particular screen size or resolution.
The platform therefore assumes a single calibrated participant display and a binocular Tobii tracker, but fixes no resolution, and the same ingest path carries the simulated mouse source of \cref{sec:impl-sensing-modes}, which produces the identical normalised \texttt{GazeData} by another route.

\subsection{Calibration and validation}
\label{sec:impl-calibration}

Calibration is one of the four readiness gates of \cref{sec:impl-session} (\cref{fig:impl-calibration}); this section opens how it produces the quality metrics the researcher sees and the gate consults.
The flow is two-phase and is orchestrated by a \texttt{CalibrationService} that talks to the eye tracker only through the sensing port, never the SDK directly.
In the first phase the participant fixates the points of the selected preset while the tracker collects data, after which a calibration is computed and applied; the researcher can choose a 9-, 13-, or 16-point preset, and the choice is persisted so it survives a restart (FR3.5).
In the second phase the participant fixates five fixed validation targets and the tracker is asked, through the same port, to compute the accuracy and precision of the now-applied calibration.
Throughout, the service pauses gaze streaming, broadcasts the calibration snapshot after every step so both screens follow along, and leaves the application untouched between participants, so a recalibration is just another call rather than a restart (FR3.4).

The metrics themselves are computed in the Tobii adapter, which keeps the eye-tracker-specific geometry on the infrastructure side of the port (\cref{lst:impl-validation}).
Accuracy is the angular offset between where the eye actually looked and the validation target, measured from the eye's gaze origin; precision is the root-mean-square of the angular change between successive samples, that is, the jitter while the participant holds a single target.
These two degree values, together with a quality grade, are the figures shown to the researcher before the session can start (FR3.2): a point is graded \emph{good} below \ang{0.5} accuracy and \ang{0.3} precision and \emph{fair} below \ang{1.0} and \ang{0.5}, and a validation passes only when the averages stay within the \emph{fair} bounds and at least four fifths of the points pass.
Only a passing validation satisfies the calibration gate, and its accuracy, precision, and grade are carried in the setup snapshot into the session record for reproducibility (FR3.3); the values measured on real hardware are reported in \cref{ch:evaluation}.

\begin{listing}[htbp]
\begin{minted}{csharp}
// Accuracy: angular offset between the eye->target ray and the eye->gaze ray,
// both measured from the eye's gaze origin (degrees).
private static double? CalculateAngularAccuracyDegrees(ValidationEyeSample s, Point3D target) =>
    CalculateAngleDegrees(CreateVector(s.GazeOrigin, target),
                          CreateVector(s.GazeOrigin, s.GazePointInUserCoordinates));

// Precision: RMS of the angle between successive gaze samples, i.e. the jitter
// while the participant holds one validation target (degrees).
private static double? CalculatePrecisionDegrees(IReadOnlyList<ValidationEyeSample> samples)
{
    if (samples.Count < 2) return null;
    var deltas = new List<double>(samples.Count - 1);
    for (var i = 1; i < samples.Count; i++)
    {
        var previous = samples[i - 1];
        var current = samples[i];
        var delta = CalculateAngleDegrees(
            CreateVector(previous.GazeOrigin, previous.GazePointInUserCoordinates),
            CreateVector(current.GazeOrigin, current.GazePointInUserCoordinates));
        if (delta.HasValue) deltas.Add(delta.Value);   // skip degenerate pairs
    }
    return deltas.Count == 0 ? null : Math.Sqrt(deltas.Average(d => d * d));   // RMS
}

// Shared geometry: the angle between two 3-D rays via the dot product, in degrees.
private static double? CalculateAngleDegrees(Vector3 from, Vector3 to)
{
    if (from.Magnitude <= double.Epsilon || to.Magnitude <= double.Epsilon) return null;
    var cos = (from.X*to.X + from.Y*to.Y + from.Z*to.Z) / (from.Magnitude * to.Magnitude);
    return Math.Acos(Math.Clamp(cos, -1d, 1d)) * 180d / Math.PI;   // clamp guards acos domain
}

private static Vector3 CreateVector(Point3D from, Point3D to) =>
    new(to.X - from.X, to.Y - from.Y, to.Z - from.Z);
\end{minted}
\caption{Validation accuracy and precision (abbreviated from \texttt{TobiiEyeTracker\-Adapter.cs}). Accuracy is the angle between the ray to the target and the ray to the measured gaze point; precision is the root-mean-square of the angle between every consecutive pair of gaze samples. Both reduce to one dot-product angle helper that returns null for degenerate rays, and both are averaged per eye before grading, so the core depends only on the resulting degree values and never on the eye-tracker geometry.}
\label{lst:impl-validation}

\subsection{Sensing modes and hardware-free operation}
\label{sec:impl-sensing-modes}

The sensing \emph{source} is itself a swappable module.
A sensing mode is a single setting (\texttt{eyeTracker}, \texttt{webcam}, or \texttt{mouse}) held by a small service, changed through a REST command without restarting the application (FR17.2) and persisted so it survives one.
What makes the modes interchangeable is that they all converge on the same lock-free ingest of \cref{lst:impl-hotpath}: the Tobii adapter raises a \texttt{GazeData}, and the other sources produce the identical record by another route, after which the token mapping, the eye-movement analysis, the live overlay, and the export of \cref{sec:impl-sensing} cannot tell which source produced the sample.

Mouse mode is the clearest case and the most useful one in practice (FR17.3).
In the participant reader, when the mode is \texttt{mouse}, the cursor becomes the gaze source: each pointer movement is throttled and turned into a normalised \texttt{GazeData} of exactly the shape the Tobii adapter emits (\cref{lst:impl-mousegaze}) and sent over the WebSocket.
On the backend, \texttt{SubmitMouseGazeSampleAsync} checks only that mouse mode is active and a session is running, then hands the sample to the very same \texttt{UpdateGazeSample} the hardware path uses (\cref{lst:impl-mouseingest}).
Because nothing downstream distinguishes the source, the whole platform, gaze-to-content mapping, fixations and regressions, interventions, replay, can be operated, developed, and demonstrated on any machine with no eye tracker attached, which is what made day-to-day work on this thesis possible away from the hardware.

\subsection{Context-preserving interventions}
\label{sec:impl-context}

RQ3 asks how a typographic micro-intervention can change the text while preserving the reader's context, the recovery concern raised in the literature \cite{jensen2025context}.
A change such as a larger font or a narrower measure reflows the entire document, so the line a participant was reading moves to a new position on screen, and without compensation the reader is left hunting for their place in the middle of an experiment.
\Cref{sec:impl-session} surfaced one half of our answer as an operator control: appearance changes (colour, theme) commit immediately, but a layout-changing intervention (font family, size, line width, line height, or letter spacing) waits for a chosen commit boundary so the reflow lands at a natural reading break rather than mid-line.
This section opens the other half, namely what happens to the reader's position when the reflow does land, which we realise in the participant reader as a continuous \emph{capture-and-restore} around every change (FR9).

The mechanism is a small pipeline implemented in one hook, \idtt{usePreserveReadingContext}, and it runs in two phases separated in time (\cref{fig:impl-context-seq}).
Before any intervention, the reader continuously records an \emph{anchor} for the participant's current reading position and keeps only the newest one.
When an intervention commits, the reader chooses a restore strategy from the intervention's declared effect, re-finds the anchor in the now-reflowed document, scrolls it back to the screen position it held before, measures how far off the result landed, and grades the outcome as preserved, degraded, or failed.
That grade is reported to the backend and written into the session record, so the cost of every intervention to the reader's continuity is auditable after the fact rather than only felt during the session (FR9.3).
The branching that turns a raw residual error into a graded outcome is summarised in \cref{fig:impl-context-decision}, and each stage below maps to one of the listings that follow.

\paragraph{Continuously capturing an anchor.}
The capture phase re-measures the anchor on a fixed cadence (every \SI{120}{\milli\second}) and again whenever the content changes, so a fresh anchor is almost always available the moment an intervention arrives (\cref{lst:impl-anchor-capture}, FR9.1).
\texttt{measureAnchor} chooses the most semantically specific target that is actually visible: it prefers the word the participant is currently looking at, falls back to the first word near the top of the viewport, and falls back again to the enclosing paragraph.
It records which of these three sources it used, the chosen element's sentence, token, and block identifiers, and, crucially, the element's offset from the top of the viewport, because that on-screen offset, rather than the raw scroll position, is what the restore phase will reproduce.
Each anchor also carries a capture timestamp, which lets the restore phase reject an anchor older than \SI{15}{\second} as stale rather than scroll to a position the participant has long since left.

\begin{listing}[htbp]
\begin{minted}{typescript}
// Capture the reader's current position: the word being looked at, else the first
// word near the top of the viewport, else the enclosing paragraph (FR9.1).
function measureAnchor(container: HTMLElement, content: HTMLElement): AnchorSnapshot | null {
  const view = getContainerRect(container);
  const candidate = content.querySelector("[data-gaze-active='true'][data-token-id]");
  const active = candidate && intersectsViewport(candidate.getBoundingClientRect(), view) ? candidate : null;
  const token = active ?? getFirstVisibleWord(content, view);
  if (token) {
    const rect = token.getBoundingClientRect();
    return {
      source: active ? "active-token" : "fallback-token",       // recorded; drives the restore tolerance
      anchorSentenceId: token.dataset.sentenceId ?? null, anchorTokenId: token.dataset.tokenId ?? null,
      anchorBlockId: token.closest("[data-block-id]")?.dataset.blockId ?? null,
      anchorViewportOffsetPx: rect.top - view.top,              // where it sits on screen
      scrollTopPx: container.scrollTop, capturedAtUnixMs: Date.now(),
    };
  }
  // paragraph fallback: the first block intersecting the viewport
  const block = Array.from(content.querySelectorAll("[data-block-id]"))
    .find((el) => intersectsViewport(el.getBoundingClientRect(), view));
  if (!block) return null;
  const rect = block.getBoundingClientRect();
  return {
    source: "block-anchor", anchorSentenceId: null, anchorTokenId: null,
    anchorBlockId: block.dataset.blockId ?? null, anchorViewportOffsetPx: rect.top - view.top,
    scrollTopPx: container.scrollTop, capturedAtUnixMs: Date.now(),
  };
}
\end{minted}
\caption{Capturing the reading anchor (abbreviated from \texttt{usePreserveReadingContext.ts}). The anchor prefers the gazed-at word and degrades to a visible word and then a paragraph, storing the element's identifiers and its offset from the top of the viewport so the same position can be re-found after a reflow.}
\label{lst:impl-anchor-capture}
\end{listing}

\paragraph{Choosing a restore strategy at commit.}
When an intervention commits, its declared effect selects one of two restore modes (\cref{lst:impl-restore-mode}, \cref{fig:impl-context-decision}).
A layout-affecting change (one that lists any affected presentation property) triggers a \emph{semantic restart}: because the whole document reflows, the safest reference point is not the old pixel offset but the sentence or paragraph the change committed against, which the reader re-establishes near the top of the reading area.
An appearance-only change (colour or theme) instead uses an \emph{offset preserve}, which holds the captured anchor at its exact previous offset because nothing about the layout has moved.
Two early exits avoid needless work: an appearance-only change committed at a frozen sentence or paragraph boundary moves nothing on screen, so it is reported preserved without any restore, and an offset preserve whose anchor is missing or stale cannot be compensated and is reported failed.

\begin{listing}[htbp]
\begin{minted}{typescript}
// On commit, the intervention's declared effect selects the restore strategy (FR9.2).
const restoreMode = isLayoutAffectingIntervention(latestIntervention)  // any affected layout property?
  ? "semantic-restart"     // font family / size / line width / line height / spacing: the document reflows
  : "offset-preserve";     // colour / theme: nothing moves, keep the captured offset
const boundary = latestIntervention?.appliedBoundary ?? "immediate";

// An appearance-only change at a frozen sentence/paragraph boundary moves nothing on screen:
// there is no reflow to undo, so report it preserved and skip the restore entirely.
if (restoreMode === "offset-preserve" && boundary !== "immediate" && boundary !== "page-turn") {
  onContextPreservationChange?.({ status: "preserved", anchorSource: "scroll-only", anchorErrorPx: 0, /* ... */ });
  return;
}
// An offset preserve with no fresh anchor (missing, or older than 15 s) cannot be compensated.
if (restoreMode === "offset-preserve" && !hasFreshAnchor) {
  commitFailure("Anchor snapshot was unavailable or stale.");   // status "failed"
  return;
}
\end{minted}

\paragraph{Locating the anchor after the reflow.}
Once the mode is fixed, the reader must find the anchor again in a DOM the reflow may have rebuilt (\cref{lst:impl-anchor-locate}, FR9.2).
For an offset preserve, \texttt{locateAnchor} degrades through the same three levels the capture used, in order of decreasing precision: it tries the recorded sentence, then the token, then the block, returning the first that still exists together with the source it resolved to.
For a semantic restart, \idtt{locateSemanticRestartAnchor} instead resolves the sentence or block the intervention committed against, so the reader resumes from the start of that segment.
If nothing can be located, the reader does not guess: it reports failed, or, when a stale anchor still exists, restores the previous scroll position only and reports the weaker degraded outcome with an anchor source of \texttt{scroll-only}.
Recording the resolved source matters because it feeds directly into how strictly the next step grades the result.

\begin{listing}[htbp]
\begin{minted}{typescript}
// Re-find the captured anchor in the reflowed DOM, degrading sentence -> token -> block (FR9.2).
function locateAnchor(content: HTMLElement, anchor: AnchorSnapshot): LocatedAnchor {
  const offset = anchor.anchorViewportOffsetPx;
  if (anchor.anchorSentenceId) {
    const els = findSentenceElements(content, anchor.anchorSentenceId);
    if (els.length) return { anchorSource: "sentence-anchor", primaryElement: els[0], anchorElements: els,
                             anchorViewportOffsetPx: offset, reason: null };
  }
  if (anchor.anchorTokenId) {
    const token = content.querySelector(`[data-token-id="${escapeAttributeValue(anchor.anchorTokenId)}"]`);
    if (token) return { anchorSource: anchor.source === "active-token" ? "active-token" : "fallback-token",
                        primaryElement: token, anchorElements: [token],
                        anchorViewportOffsetPx: offset, reason: "Sentence anchor unavailable." };
  }
  if (anchor.anchorBlockId) {
    const block = content.querySelector(`[data-block-id="${escapeAttributeValue(anchor.anchorBlockId)}"]`);
    if (block) return { anchorSource: "block-anchor", primaryElement: block, anchorElements: [block],
                        anchorViewportOffsetPx: offset, reason: "Semantic anchors unavailable." };
  }
  return null;                  // caller reports "failed", or scroll-only "degraded" if a stale anchor exists
}

\paragraph{Re-aligning and grading the outcome.}
With the anchor located, the reader re-aligns the viewport and measures the result (\cref{lst:impl-anchor-restore}).
It scrolls so the located element returns to the offset stored at capture, then measures the residual \texttt{anchorErrorPx} as the distance, in pixels, between where the element actually landed and where it should have.
The residual is graded against a tolerance that depends on both the restore mode and the anchor source (\cref{fig:impl-context-decision}): a semantic restart is preserved within 72 pixels, whereas an offset preserve is preserved only within 48 pixels when it resolved to a precise sentence anchor, and is treated as degraded beyond 120 pixels or whenever it could only fall back to a coarse block anchor.
This asymmetry encodes a deliberate judgement on our part: a coarse anchor or a full reflow earns a wider tolerance, because demanding pixel-exact restoration there would label a perfectly acceptable resume as a failure.

\begin{listing}[htbp]
\begin{minted}{typescript}
// After the change, re-find the anchor (mode-dependent) and scroll it back to the same
// on-screen offset; if it cannot be found, restore scroll only and report it (FR9.2).
const located = restoreMode === "semantic-restart"
  ? locateSemanticRestartAnchor(content, latestIntervention)   // the sentence/paragraph the change committed against
  : locateAnchor(content, anchor);                             // the captured anchor: token -> sentence -> block
if (!located) { commitFailure("Anchor was unavailable or stale."); return; }   // status "failed"

const view = getContainerRect(container);
const currentTop = located.primaryElement.getBoundingClientRect().top - view.top;
container.scrollTop += currentTop - located.anchorViewportOffsetPx;    // re-align to the captured offset

const finalTop = located.primaryElement.getBoundingClientRect().top - view.top;
const anchorErrorPx = Math.abs(finalTop - located.anchorViewportOffsetPx);

// Tolerance depends on the restore mode and on which anchor we fell back to.
const status =
  restoreMode === "semantic-restart"
    ? (anchorErrorPx <= 72 ? "preserved" : "degraded")
    : located.anchorSource === "sentence-anchor" && anchorErrorPx <= 48 ? "preserved"
    : anchorErrorPx > 120 || located.anchorSource === "block-anchor"    ? "degraded"
    : "preserved";
onContextPreservationChange?.({ status, anchorErrorPx, anchorSource: located.anchorSource, /* ... */ });
\end{minted}
\caption{Restoring the reading anchor (abbreviated from \texttt{usePreserveReadingContext.ts}). The reader re-finds the anchor (degrading from sentence to token to paragraph), scrolls it back to its captured offset, measures the residual error, and reports the outcome, which the backend records in the session log.}
\label{lst:impl-anchor-restore}
\end{listing}

\paragraph{Closing the loop.}
Two things happen once the outcome is known.
When a semantic restart has highlighting enabled, the reader briefly flashes the restored sentence so the participant's eye is drawn back to where they should resume, then fades it after about \SI{3}{\second}.
Independently, the graded outcome is handed to \idtt{onContextPreservationChange}, which sends it to the backend, where it is appended to the session log next to the triggering intervention, checkpointed, and carried into the export as a \idtt{ReadingContextPreservationEventSnapshot} (FR9.3), following the same gate-and-record shape as every other state change (\cref{lst:impl-state-change}).
Because the outcome of every intervention is recorded with its residual error and anchor source, a later analysis can ask not just whether an intervention helped a reader but what it cost them in lost position, which is exactly the kind of auditable evidence RQ4 asks the platform to produce.

\subsection{Experiment templates and session sequencing}
\label{sec:impl-templates}

For RQ4 the platform has to let a researcher define a repeatable experiment, not just a single reading.
An experiment template is a named, ordered sequence of items (\cref{fig:impl-template}); each item references one reading material from the library and may carry its own typographic configuration, so the same text can be presented differently across conditions (FR15.1, FR15.2).
Templates are persisted and reusable across sessions and participants (FR15.3), which is what makes a run reproducible from a stored definition rather than reassembled by hand each time.

A session may then play through the whole sequence rather than a single item (FR16.1).
When the session starts, the manager resolves the running order from the template (\cref{lst:impl-order}): in \texttt{fixed} mode it keeps the authored order, and in \texttt{random} mode it shuffles the items and re-indexes them, which is the counterbalancing a within-subject comparison of interventions needs.
The resolved first item becomes the active reading content, the rest follow in order, and each transition between items is written into the session log as a timestamped event (FR16.2), so the sequence the participant actually saw is recoverable from the record.

\subsection{Record, export, and replay}
\label{sec:impl-replay}

The auditable record is the other half of RQ4, and it is what \cref{sec:impl-session} sealed at the end of a session.
Everything the walkthrough produced, every raw gaze sample, every derived fixation, saccade, and regression, every intervention and context-preservation outcome, every lifecycle and quiz event, is written into a single export document with a versioned manifest that names the schema, its version, and the producer (down to the Tobii SDK version), alongside the calibration metrics and the presentation configuration (FR12.5).
At finish, two such documents are built, a full raw export and a processed one, so downstream analysis can take either the unabridged record or a flattened summary.

A document serialises to JSON or to CSV through CsvHelper (\cref{lst:impl-export}, FR12.4).
The CSV is not a lossy flattening: alongside the per-event rows it carries the entire export as a base64-encoded JSON payload in a dedicated row, so a spreadsheet-friendly CSV is still a fully replayable record and the two formats round-trip to the same document.
On import, the front-end reconstructs a session from such a file but first checks that the manifest schema and version are ones it can interpret (\cref{lst:impl-import}, FR21.1), rejecting anything else rather than mis-rendering it; this version gate is what lets the format evolve without silently breaking old recordings.

Replay then reconstructs the reading view as a timed playback (\cref{fig:impl-replay}).
Because every event stream is ordered by time, the player can build the exact frame at any instant by binary-searching each stream for the latest event at or before the playhead, which is what gives scrubbing, variable-speed playback, and jump-to-event navigation with intervention markers on the timeline (FR21.2--FR21.4).
Finally, durability does not depend on a clean finish: during a run a checkpoint worker periodically persists the live session state, so an interrupted session can be detected and offered for recovery on the next start rather than lost (FR22).
Together the versioned record, the dual-format export, the version-gated import, and the deterministic replay are what make a session on this platform reproducible and comparable after the fact, which is the auditability RQ4 asks for.
