# Reader Shell & UI

The platform is operated as two browser surfaces served by one Next.js front-end: the **participant reader** on one screen and the **researcher console** on the other. The participant only ever sees the text; the researcher sees a live mirror of that text with analysis overlays and the controls that steer the session. The two never talk to each other: both render the same backend-owned snapshot, which is what keeps them consistent without drift.

## The participant reader

The reader renders Markdown content from the presentation carried on the session snapshot. On an active session it registers itself as the participant view, maps each gaze sample to a word against the live DOM (see [Sensing Layer](/system-design/sensing-layer/)), and streams the enriched observation back over the WebSocket. When an intervention commits, the [capture-and-restore mechanism](/system-design/intervention-layer/) holds the reading position across the reflow. Deliberately, the reader carries no researcher controls and no session chrome: plain text, nothing to distract the participant.

## The researcher console

The console renders from the same live snapshot through the same hook, and adds:

- a **mirror** of the participant's text with the live gaze position drawn over it,
- **analysis overlays**: a fixation heat map, the recent saccades, and the regression count, so the researcher sees not only where but how the participant is reading,
- the **intervention and typography controls**, from which a manual intervention is pushed over the WebSocket,
- the **decision-mode controls** (manual, advisory, autonomous) and the approve / reject surface for pending proposals,
- **session health**: live sample rate, gaze validity, and round-trip latency.

Session setup runs through a gated stepper (participant, licensed eye tracker, passed calibration, reading material); the backend re-checks the same gates at start, so readiness is enforced by the server, not just reflected in a disabled button.

## How live state reaches both screens

One shared WebSocket client (`gaze-socket.ts`) connects lazily, requests current state on open, and routes every inbound envelope through a single handler. Both surfaces consume it through one hook, `useLiveExperimentSession`, which coalesces snapshot bursts to **one React commit per animation frame** (about 60 Hz): the UI renders the newest snapshot at display rate regardless of the inbound message rate, and nothing is dropped from the record, because analysis and persistence consume the stream before the rendering boundary. High-frequency gaze state stays out of Redux by design and flows through refs and requestAnimationFrame loops.

## Per-context settings

The participant reading view, the researcher mirror, and the replay view each keep independent typographic and appearance settings, persisted separately, so enlarging the researcher's mirror never changes what the participant sees (FR23).
